# 项目数据采集包

用途：把《项目经历》里所有【待实测】数字测出来。**脚本在你的 Linux 实验机上运行**，与本机（Windows）无关。

## 一、脚本与项目对应关系

| 脚本 | 对应项目 | 采集的数字 |
|---|---|---|
| 01_vip_failover.sh | 第 1 条 | VIP 漂移耗时、业务请求成功率、业务中断时长 |
| 02_mysql_replication_delay.sh | 第 2、7 条 | MySQL 主从复制延迟（空闲 + 压测） |
| 03_k8s_hpa_scale.sh | 第 5 条 | HPA 扩容/缩容耗时（配合压测取 QPS） |
| 04_prometheus_stats.sh | 第 4、6 条 | 采集目标数、告警规则条数、firing 告警数、看板数 |
| 05_alert_e2e_latency.sh | 第 4、6 条 | 告警端到端时延 |
| 06_api_and_deploy_time.sh | 第 1、7、9 条 | 接口响应时间、容器数量、部署耗时 |

## 二、使用方法

```bash
# 1. 把整个文件夹拷到实验机
scp -r 项目数据采集包 user@192.168.x.x:/root/

# 2. 赋权
cd 项目数据采集包 && chmod +x *.sh

# 3. 按需运行，把输出的数值抄进简历对应位置
bash 01_vip_failover.sh 192.168.10.100 / 100
```

## 三、参考区间（只用于判断测量是否合理，**不要照抄**）

| 数字 | 实验环境常见区间 | 说明 |
|---|---|---|
| VIP 漂移耗时 | 0.5–3 秒 | 默认 advert_int 1s 时，通常 1 个通告周期内完成 |
| 业务请求成功率 | 95%–100% | 采样间隔 0.2s 时，中断 1–2 个请求属正常 |
| MySQL 主从延迟（空闲） | 0–1 秒 | 空闲时 Seconds_Behind_Master 常为 0，写成「<1 秒」更稳 |
| MySQL 主从延迟（压测） | 几十 ms–数秒 | 取决于写入压力与从库配置 |
| HPA 扩容耗时 | 30–90 秒 | 含 15s 指标同步周期与镜像拉取时间 |
| 单机压测 QPS | 200–2000 | 取决于接口复杂度与虚拟机核数 |
| 接口响应时间 | 5–200 ms | 本地网络 + 简单查询 |
| 告警端到端时延 | 30–90 秒 | 含 scrape interval + 规则评估 + for 时长 + 分组等待 + Webhook |

**说明**：这些是「合理值」的参考，不是你的数据。测出来和区间差很远也没关系，真实即可；但如果差一个数量级，先检查是不是看错了单位或指标。

## 四、【待确认】类数据自查清单（不需要脚本）

- 第 1 条：虚拟机规格；Keepalived 的 priority / advert_int / auth_type（`cat /etc/keepalived/keepalived.conf`）；upstream 权重与健康检查参数（`cat /etc/nginx/conf.d/*.conf`）；检测脚本里的失败阈值（`cat check_nginx.sh`）
- 第 2 条：团队人数；7 台节点规格；Keepalived/HAProxy 参数；巡检脚本的检查项数量（`grep -c` 数一下）；集群连续运行时长
- 第 3 条：5 台节点规格；防火墙放通端口与网段（`firewall-cmd --list-all`）
- 第 4 条：采集目标数（`curl -s http://<prom>:9090/api/v1/targets`）；调整过阈值的规则条数
- 第 5 条：master/worker 数量与规格；Pod 跨节点不通的真实根因；ES 加权字段与权重；HPA 阈值与最大副本数（`kubectl get hpa -o yaml`）
- 第 6 条：告警规则条数（`grep -c "alert:" *.rules.yml`）；for 时长；看板数量
- 第 7 条：容器数量；稳定运行时长
- 第 8 条：使用人数
- 第 10 条：文档篇数；向量库名称；embedding 模型名称

## 五、没有脚本能测的两处（只能靠你回忆 / 估算）

- 第 8 条「信息处理耗时由 __ 降至 __」：这是主观效率对比，建议直接删掉这半句，不与量化，风险更低。
- 第 10 条「检索命中率」：抽样 20 个问题人工判定即可，命中几个就是几个，写「抽样 20 个问题命中 16 个」比写百分比更可信。
